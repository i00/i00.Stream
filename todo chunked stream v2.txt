CORRECTNESS
- C1  Anchor IDs are reused after a checkpoint rollback. Checkpoints.vb RestoreCheckpointState
      does `_NextAnchorId = State.NextAnchorId` (resets the counter downward). Make it monotonic:
      `_NextAnchorId = Math.Max(_NextAnchorId, State.NextAnchorId)` (same for _NextPhysicalRecordId
      for consistency - lower risk since it is internal). Add a test: create anchor inside a
      checkpoint -> rollback -> create another -> assert the ids differ.

- C3  BuildExtentsFromBuffer / BuildCloneExtents write + refcount physical records BEFORE the
      guards that could reject the resulting extents (ReplaceRangeCore's
      InsertLength <> ActualLength, RebaseExtentLogicalOffsets' duplicate-anchor / length checks).
      A firing guard would orphan those records. Fix: move the reachable checks ahead of any
      WritePhysicalRecord call (InsertLength is knowable from the input without materialising
      records). Let C2's fault flag be the backstop for the "shouldn't happen" ones.

- C4  Lz4Block.vb ReadExtendedLength: `Length += Value` has no cap -> OverflowException (VB
      checked arithmetic) on a long run of 0xFF bytes. Cap it and throw InvalidDataException,
      the way Snappy already does (explicit caps + ULong accumulation).

- C6  [FIXED 2026-08-28] Orphaned physical-record leak (found via _Samples .../bin/Debug/Test.efs;
      "Test - Cant be defragged.efs" preserved as the repro). A 370 MB stream held 4,389
      physical-record entries with RefCount = 0 that no extent referenced. Root cause: when a
      record's refcount hit 0 during a checkpoint, DecrementPhysicalRecordRefCount parked it in
      _PendingReclaimedPhysicalRecords; but (a) ReclaimPendingPhysicalRecords bailed on
      `If HasOpenCheckpoint Then Return` and CommitCheckpointCore does not pop the checkpoint on
      commit, so it NEVER ran, and (b) RestoreCheckpointState (called on every rollback AND on
      dispose-of-a-committed-checkpoint) then DiscardPendingPhysicalRecordReclaims()'d the list.
      So every CreateCheckpoint -> overwrite/delete -> Commit -> Dispose leaked every record the
      edit freed. EmbeddedFileSystem wraps ~every mutation in a checkpoint, hence thousands.
      Fix: guard is now `_CheckpointStack.Count > 1`; CommitCheckpointCore reclaims BEFORE the
      durable publish + baseline capture; RestoreCheckpointState now REBUILDS the pending set
      from the restored records (RefCount <= 0) instead of discarding it, so inner-checkpoint
      frees survive to the outermost finalise. Tests: CheckpointCommitReclaimsFreedPhysicalRecords,
      NestedCheckpointCommitsReclaimFreedPhysicalRecords,
      OuterRollbackRestoresRecordsFreedByCommittedInnerCheckpoint (Transactions.vb). Defrag also
      still sweeps unreferenced records first (Defrag.vb) as a backstop / to clean pre-existing
      bad files.

- C7  [PARTLY ADDRESSED 2026-08-28] In-checkpoint chunk writes now reuse free holes.
      Shipped: (1) GetNextWriteOffset no longer force-appends chunk records while a
      checkpoint is open - they run the normal BestFit/FirstFit hole search (the *Scan
      rebuild stays disabled mid-checkpoint: it would count a checkpoint-deleted record as
      free). Safe: a rollback/crash reloads the pre-checkpoint durable generation, which
      does not reference the hole, so the bytes are harmless free space; a commit publishes
      metadata that makes them live. (2) FreeSpaceAllocator.TryAllocate gains a MinOffset;
      in-checkpoint metadata is confined to holes >= the outermost checkpoint mark so small
      metadata pages don't fragment the big pre-checkpoint holes. (3) Checkpoint.State is
      captured AFTER WriteCheckpointRecoveryState in create/commit/rollback so the deferred
      span that header rotation releases survives the close-time RestoreCheckpointState -
      previously, in a checkpoint-only workload nothing else rotated the header so freed
      space never re-entered _FreeSpaces until a Defragment. Tests: Transactions.vb
      CheckpointChunkWriteReusesFreeHole / CheckpointHoleFillingWriteRolledBackRestoresState
      / ...AbandonedRecoversToBaseline; Allocation.vb
      CheckpointChunkAllocationPreservesDataUnderEveryPolicy (replaces the obsolete
      AllocationInsideCheckpointDoesNotReuseCommittedHole). Verified: 2 MB write into a
      freed 2 MB hole inside a checkpoint grows the file ~23 KB (metadata) instead of 2 MB.
      205/205 + fuzzer green.

      STILL NOT FIXED - the EFS create/delete cycle (~280 KB/cycle): that workload's growth
      is METADATA PAGE CHURN, not chunk placement. Every EFS op is its own checkpoint commit
      and each relocates ~2-4 dirty ~8 KB paged-metadata pages (COW; adding a record shifts
      ordinals and dirties every later page). With the new policy the file records DO reuse
      the deleted-file holes, but the relocated metadata now pure-appends (it can't fill a
      hole below the mark) and _IndexOffset (commit sets it to Math.Max(BaseStream.Length,
      dataEnd)) ratchets up to swallow it - net growth unchanged for THAT workload. Kris is
      removing checkpoints from EmbeddedFileSystem entirely (PendingFile state + crash
      cleanup detection instead), which sidesteps it. Remaining levers if EFS growth still
      bites: (a) cut the number of metadata relocations - write an unchanged-size dirty page

      Also saw _PhysicalDataEnd stale-high drift in the EFS run (PDE stuck ~2 MB after

- C5  ExtentReclaimType.Scan (WIP): ReclaimUnreferencedPhysicalRecordsByScan bails on

- D5  Defragment(Move / Sequence): RelocatePhysicalRecord does ~4-5 fsyncs + a metadata-root
